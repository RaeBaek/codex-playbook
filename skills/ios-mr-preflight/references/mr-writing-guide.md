# MR 작성 기준

MR 설명을 작성할 때 읽으세요. 저장소의 PR/MR 템플릿을 우선하고, 없으면 [기본 PR/MR 템플릿](mr-template.md)을 사용하세요.

## 변경 설명

- 요약에는 구체적인 문제나 요구사항과 변경 후 동작을 먼저 적으세요. 동작 수정이라면 어떤 조건에서 이전에는 어떻게 동작했고 이제 어떻게 달라지는지 설명하세요.
- 사용자에게 보이는 동작 변화가 없는 내부 변경은 실제 목적과 영향을 적으세요. 확인되지 않은 성능 개선이나 안정성 향상을 주장하지 마세요.
- 주요 변경 사항에는 리뷰 판단에 필요한 구현 차이만 적으세요. diff의 파일 목록이나 함수 이름을 나열하는 것으로 설명을 대신하지 마세요.
- 관련 이슈나 요구사항은 제공되었거나 직접 확인한 경우에만 연결하세요. 변경 이유가 코드만으로 확인되지 않으면 의도를 추정하지 말고 미확인 사항으로 남기세요.
- 최종 변경 범위를 기준으로 작성하세요. 작업 중 대화, 폐기한 접근, 범위 밖 문제는 최종 구현의 판단에 필요할 때만 포함하세요.

## 비교 범위와 검토 결과

- 기준 브랜치와 비교 대상 브랜치 또는 커밋, 실제 사용한 diff 범위를 식별할 수 있게 적으세요. 브랜치 이름이나 원격 추적 정보가 없으면 추측하지 마세요.
- MR의 병합 기준점부터 비교하는 diff와 두 커밋 상태를 직접 비교하는 diff는 범위가 다를 수 있습니다. 사용자가 지정한 비교 방식이나 확인한 MR diff를 따르세요.
- 미커밋 변경을 포함하도록 요청받았다면 스테이징·미스테이징·관련 새 파일의 포함 여부를 설명하고, 브랜치에 이미 포함된 변경과 구분하세요.
- 제출 전 점검에서 발견한 결함이나 미확인 조건은 설명 초안과 구분해 사용자에게 알리세요. 문제를 발견해도 임의로 수정하지 마세요.
- 실제 실행 없이 빌드 가능, 테스트 통과, 회귀 없음으로 단정하지 마세요. 정적 검토 결과와 실행 검증 결과를 구분하세요.
