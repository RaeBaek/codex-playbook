# 수동 검증 항목 작성 기준

MR에 수동 검증 항목을 제안할 때 읽으세요. 변경된 분기와 직접 영향을 받는 경로에서 확인할 항목만 선택하세요.

## 항목 구성

각 항목은 사람이 실행하고 결과를 판별할 수 있도록 다음 요소를 담으세요.

- 조건: 변경된 경로에 진입하는 데이터, 권한, 화면 상태 등 필요한 전제.
- 행동: 사용자가 실제 수행할 조작 또는 재현 순서.
- 기대 결과: 화면·데이터·오류 처리 등 관찰 가능한 결과.

예를 들어 중복 요청 방지가 변경된 경우:

```markdown
- [ ] 응답이 지연되는 상태에서 저장 버튼을 연속으로 눌렀을 때, 저장 요청이 중복 발생하지 않고 완료 결과가 한 번 표시된다.
```

이 예시는 형식을 설명하기 위한 것입니다. 실제 diff에 관련 변경이 없다면 추가하지 마세요. 요청 수처럼 UI에서 직접 보이지 않는 결과는 확인 가능한 기존 로그나 관찰 수단이 있는지 고려하고, 이를 위해 코드를 임의로 추가하지 마세요.

## 변경에 따른 선택

- 조건 분기가 바뀌면 정상 경로와 실제 바뀐 경계 조건을 확인하세요.
- 비동기 처리나 수명이 바뀌면 화면 이탈·재진입, 연속 입력, 늦은 응답 중 영향을 받는 시나리오를 선택하세요.
- 실패 처리가 바뀌면 관련 실패 조건에서 표시와 재시도 결과를 확인하세요. 모든 변경에 오프라인·재시도를 일괄 추가하지 마세요.
- UI 배치나 문구가 바뀌면 해당 변경에 영향을 받는 글자 크기, VoiceOver, 언어 또는 화면 크기를 선택하세요. 작은 수정을 전체 접근성 점검으로 확대하지 마세요.
- 저장이나 삭제 경로가 바뀌면 완료 후 다시 조회했을 때의 데이터 상태 등 직접 영향을 받는 일관성을 확인하세요.

## 검증 상태

- 제안만 한 항목과 실행 결과를 확인하지 못한 항목은 `[ ]`로 두세요.
- 사용자가 해당 항목의 통과를 알려주었거나, 명시적으로 허용된 실행으로 직접 통과를 확인한 항목만 `[x]`로 표시하세요. 일부 결과를 전체 체크리스트의 통과로 확대하지 마세요.
- 실패한 항목은 `[ ]`로 두고 관찰된 실패 결과를 함께 적으세요.
- 정적 코드 검토로 판단한 사항은 실행 통과 항목으로 체크하지 마세요. 빌드·테스트를 실행하지 않았다면 그 사실을 명시하세요.
