# Swift 변경 코드 리뷰

## 검토 절차

1. 요청에서 변경 의도와 검토 대상을 확인하세요. 기준 브랜치나 커밋이 지정되면 그 범위의 diff를 사용하세요. 범위가 없다면 현재 작업 트리의 변경(스테이징된 변경 포함)과 관련 새 파일을 확인하세요. 이때 `python3 <이 스킬 경로>/scripts/collect_changes.py --repo <저장소 경로>`로 변경 목록을 수집할 수 있습니다. 목록은 diff나 코드 검토를 대신하지 않습니다. 검토할 변경을 특정할 수 없다면 비교 기준을 물으세요.
2. 변경 전후의 동작을 비교하고, 영향 판단에 필요한 직접 호출부와 기존 테스트만 읽으세요. 정상 경로와 경계·실패 조건에서 상태 전이, 오류 처리, 반환값이나 콜백의 계약이 의도대로 유지되는지 확인하세요.
3. 변경이 비동기 실행, UI 상태, 객체 수명, 버전별 API에 영향을 줄 때만 관련 위험을 확인하세요. 비동기 작업이나 actor 격리, 취소, 객체 수명에 영향을 주는 변경은 [동시성 검토 기준](references/concurrency-review.md)을 참고하세요. 변경으로 새로 생기거나 악화된 문제에 집중하세요.
4. 사용자에게 보이는 오동작, 데이터 손실, 크래시 등 구체적인 영향이 있고 코드로 뒷받침할 수 있는 문제를 보고하세요. 변경된 분기에 회귀 위험이 있고 기존 테스트가 이를 다루지 않으면 확인할 시나리오를 제안하세요.

## 변경 수집 도구

- `scripts/collect_changes.py`는 Git과 Python 3 표준 라이브러리만 사용하며, 작업 트리의 스테이징·미스테이징·미추적·충돌 파일 목록을 JSON으로 출력합니다. 경로는 저장소 루트 기준입니다.
- 지정한 브랜치·커밋 비교용 도구가 아닙니다. 사용자가 비교 범위를 정했다면 해당 Git diff 또는 PR diff를 직접 확인하세요.
- 파일 내용을 읽거나 변경하지 않습니다. 미추적 파일은 관련 소스인지 판단한 뒤 필요한 파일만 읽고, 비밀 정보가 담긴 파일은 수집 대상에서 제외하세요. Git에서 무시한 파일과 하위 모듈 내부의 개별 파일은 목록에 포함하지 않습니다.
- 이름 변경은 이전 경로와 새 경로로 나누어 표시합니다. 실제 diff에서는 이름 변경 여부와 내용을 확인하세요. 스테이징과 미스테이징에 같은 파일이 있으면 양쪽 변경을 모두 확인하세요.
- 실행할 수 없으면 Git 읽기 명령으로 같은 범위를 확인하세요. 도구 오류를 변경 없음으로 처리하지 마세요.

## 결과 형식

- 영향이 큰 문제부터 정리하고, 각 항목에 파일과 줄 번호, 발생 조건, 영향을 적으세요. 변경된 코드에서 근거가 되는 줄을 우선 가리키세요.
- 지적할 문제가 없으면 검토한 범위와 주요 확인 사항을 짧게 알려주세요. 정적 검토만으로 판단할 수 없는 동작은 수동 확인 항목으로 구분하세요.
- 리뷰는 읽기 전용으로 진행하세요. 수정, 빌드, 테스트 실행은 각각 명시적인 요청이 있을 때만 수행하세요.
