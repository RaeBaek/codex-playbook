# Swift 동시성 검토 기준

비동기 작업, UI 상태 갱신, actor 격리 또는 객체 수명에 영향을 주는 변경에서만 읽습니다. 아래 항목을 모두 지적 사항으로 만들지 말고, 변경으로 발생하는 구체적인 실행 경로를 확인하세요.

## 실행 컨텍스트와 격리

- UI 상태를 쓰는 코드가 기존 프로젝트의 메인 스레드·`MainActor` 계약을 유지하는지 확인하세요. `Task {}`라는 이유만으로 메인 actor 실행을 가정하지 말고 생성 위치의 격리와 호출 흐름을 확인하세요.
- `await` 전후에 다른 작업이 상태를 바꿀 수 있는지 확인하세요. 결과 적용 시 화면·요청·선택 항목이 여전히 같은지 살펴보세요. actor 내부여도 중단 지점 사이의 상태가 그대로 유지된다고 가정하지 마세요.
- `Task.detached`, 콜백, 스트림 등 실행 경계가 바뀌면 공유 상태 접근과 전달 값의 격리 조건을 확인하세요. 프로젝트의 Swift 언어 모드와 동시성 설정에 따라 진단이 달라질 수 있으므로 이름만 보고 오류를 단정하지 마세요.

## 작업 수명과 취소

- 작업이 화면 또는 객체와 함께 끝나야 하는지, 화면을 떠난 뒤에도 계속되어야 하는지 기존 동작과 요구사항으로 판단하세요.
- 반복 요청에서 이전 작업의 늦은 응답이 최신 결과를 덮어쓰는지 확인하세요. 취소 호출 여부뿐 아니라 취소 이후의 응답 적용 경로도 살펴보세요.
- 취소는 협력적으로 처리됩니다. 호출한 API가 취소를 전달하는지, 취소를 일반 실패로 표시하거나 취소 이후에도 상태를 갱신하는지 확인하세요.
- `Task {}`로 만든 작업이 호출한 작업이나 객체의 수명 종료만으로 취소된다고 가정하지 마세요. SwiftUI의 작업 modifier, 저장된 task handle 등 실제 관리 방식을 확인하세요.

## 객체 수명과 자원 정리

- 객체가 task handle이나 구독을 보관하고 작업이 객체를 캡처할 때, 실제 종료 시점과 해제 경로를 확인하세요. 유한한 작업의 강한 캡처를 곧바로 영구적인 참조 순환으로 단정하지 마세요.
- `weak self`를 사용해도 `await` 이전에 강한 참조로 승격하여 장시간 유지하는지 확인하세요. 무한 스트림이나 반복 작업은 특히 수명 관계를 살펴보세요.
- 구독·리스너·타이머가 변경된 수명에 맞게 해제되는지, 화면 재진입 때 중복 등록되는지 확인하세요.

## 보고 근거

문제가 성립하는 호출 순서나 사용자 행동, 현재 코드의 실패 지점, 사용자 영향을 설명하세요. 격리나 지원 API가 불확실하면 프로젝트 선언·설정 또는 공식 문서로 확인하고, 확인되지 않은 위험은 확정된 결함과 구분하세요. 실행 검증이 필요한 경우 수동 확인 항목으로 남기고 빌드·테스트를 임의로 실행하지 마세요.
